> **Deutsche Version:** [performance-history.md](../../de/benchmarks/performance-history.md)

Running record of all performance milestones and measurements.
**Maintenance note:** For every relevant change (llama.cpp flags,
calibration, hardware, new models), add a milestone and extend the
per-model tables with current data points. Sources: the session
statistics (`*( TTFT: … PP: … tok/s … )*` in
`data/sessions/*.json`), llama-bench runs and direct API measurements
(`timings` from `/v1/chat/completions`). The comparable session tables are
generated by `scripts/session_speed_stats.py` — the comparison rules live
there in exactly one place; do not extend the tables by hand.

Hardware baseline since 2026-06/07: 5 GPUs = 192 GB VRAM
(2× RTX 8000 48 GB + 3× V100 32 GB), details in the memory/setup docs.

## AIfred Model Comparison — Overnight Measurement 2026-09-14

All chat models registered in AIfred on both backends, driven through the
AIfred UI via Chrome DevTools (test user, agent AIfred, mode
"💡 Wissen" (knowledge) without web search, each question in a freshly cleared chat). Three questions
with fixed wording:

1. "Erkläre Quantenphysik in 30 Sätzen." (Explain quantum physics in 30 sentences.)
2. "Erkläre den Regenbogeneffekt in 30 Sätzen." (Explain the rainbow effect in 30 sentences.)
3. "Erkläre den Kuanda-Effekt in 30 Sätzen." (Explain the Kuanda effect in 30 sentences.) — **Trick question**: the
   Kuanda effect does not exist. Passed if the model recognizes and explains the
   Coandă effect or rejects the term; failed on invention or
   rambling.

requests of a turn). Per-model settings as stored in AIfred

prompt cold (~3,350 tokens). Questions 2 and 3 mostly hit the prefix cache and
compute only a few hundred tokens — their PP rates are not comparable with question 1

### Assessment

- **Quality does not come from the storage path.** Under greedy sampling
  all three paths produce bit-identical texts (probes 4/4, see v100-skinny
  `docs/PLE-KASKADE-ENTWURF.md`). In chat, sampling uses temperature, so each
  answer is a new draw from the same distribution — ranking and
  slip-ups (Chinese characters, English word fragments) are the model's
  variance. The two SSD runs show this: same path, same questions,
  different errors.
- **Prefill** is at 520–620 tok/s on all paths, cold or warm; only
  the first Classic answer after the cold compile is lower
  (468 tok/s). Both SSD runs hold 621–622 tok/s at 17,633 tokens.
- **Decode depends on the text; the storage path costs little.** The raw
  TG values scatter between 37–50 tok/s because, depending on the text, MTP hits 28–45% of the
  draft tokens. Normalized to the acceptance rate (table above), the cascade
  costs 1% compared with the old path and the SSD tier another 4%. The
  37 tok/s for Rainbow and Kuanda are thus explained for the most
  part by the low acceptance rate of these answers (28%), not by
  the disk: both SSD runs hit the same rate and
  the same speed on the same questions.
- **A cold page cache changes nothing measurable.** In the cold run the SSD rows
  demonstrably came individually from the disk (table above), yet
  the steps/s are 0.5% above the first SSD run. The store rows
  loaded cold in 25.8 s, just as fast as in earlier boots
  (25.1–25.8 s), and the whole boot was no slower at 6:33 min (previously
  6:57 and 6:52 min). The page cache holds at most 27 GiB during boot, the
  checkpoint is 123.6 GiB: the boot reads almost everything from disk anyway,
  whether or not the cache was empty beforehand.
- **Open:** Whether the 4% of the SSD tier is due to waiting for the disk or to
  the read path itself (mmap reads in the worker instead of `index_select`
  on the card) is not separated by this measurement; that would require measuring the same
  rows once fully preloaded.

### Addendum: Classic with 3 GiB — Production from the Evening of Sep 16

The RTX 8000s had headroom on both paths: stage 0 got 5.22 GiB (cascade)
or 6.14–7.17 GiB (Classic 6 GiB) for the KV cache, 262k tokens need
1.76 GiB, and the KV pool is limited by the V100 stage anyway (645,599
tokens warm, 312,341 after a cold compile — the same on both paths). So
more of the table moves into VRAM: `VLLM_QWEN4EXP_PLE_HOST_GIB=3` without the cascade.
The yardstick is the cold compile, because a new host amount changes the
compile key.

Greedy probe (three prompts plus repetition, 260 tokens, against the reference
from Sep 15), raw data in v100-skinny `handover/2026-09-15/p4_classic_host3.json`:

| Path | PLE in VRAM per rank | Host pinned | GPU 4 | KV memory stage 0 (cold) | MemAvailable after startup | Text | Decode tok/s |
|---|---|---|---|---|---|---|---|
| Classic 6 GiB (control run) | 17.84 GiB | 12 GiB | free | 6.14 GiB | 2.5 GiB | 4/4 bit-identical | 60.1 / 56.0 / 65.9 / 60.6 |
| **Classic 3 GiB** | **20.84 GiB** | **6 GiB** | **free** | **3.15 GiB** | **8.2 GiB** | **4/4 bit-identical** | **59.7 / 56.0 / 66.3 / 60.1** |
| Cascade 2 GiB + GPU 4 | 19.60 / 19.79 GiB | 4 GiB | 4.3 GiB | 4.19 GiB | 11.8 GiB | 4/4 bit-identical | 59.0 / 54.9 / 65.0 / 58.8 |

Classic 3 GiB is as fast as the old path (−0.2% against its
control run, the cascade −2.0%), halves the pinned host RAM and leaves
GPU 4 free. The cascade frees 3.6 GiB more RAM, but costs the trips through
the offload worker; it pays off once a table clearly no longer fits into
VRAM plus an acceptable host share. Cold boot 11.7 min, error-free.

### Qwen3.8-Flash-Next 180B-A4B UD-Q6_K_XL (5 GPUs, no speculation)

First model with a **lazy-read tensor**: the PLE table
(`per_layer_token_embd.weight`, **50.7 GiB Q8_0 as ONE tensor**) stays on
disk and is read row by row. It fits on no single card
(largest = 48 GB) and cannot be split with `-sm layer` — llama.cpp
solves this via `TENSOR_READ_LAZY`, which strictly requires mmap.

**Consequence for the flags:** `--direct-io` rules out mmap and thus lazy read;
the 50.7 GiB then go into host RAM (30 GB available) → OOM kill. This
model needs `--load-mode auto`, NOT `dio`. `--mlock` has no effect:
both flags write the same field, the last one wins.

| Period | Configuration | PP | TG |
|---|---|---|---|
| Aug 27 | ctx 32K, KV f16, split 12:12:8:8:8, `--load-mode auto` (lazy) | 522 | 35.4* |
| Aug 28 | ctx 256K, split 14:14:4:8:8 (prod), **varying prompts** | — | **33.0 ± 0.6** |

\* The Aug 27 value was obtained with a **repeatedly identical** prompt. The
reliable everyday value is the Aug 28 row.

Measurement: llama-server directly (not via llama-swap), pin order
GPU0,GPU2,GPU3,GPU1,GPU4. PP = 4,333-token prompt.

**The page cache determines throughput.** The PLE table is read
lazily; how fast the model is depends on how much of it sits
in RAM (saturation at 19 GB of 50.7 GB = 37%):

| State | TG |
|---|---:|
| first run after loading (cold cache) | 22–31 |
| settled, varying prompts | **33.0** |
| settled, identical prompt repeated | 35.7 |

So after every model start, the first answer is the slowest.
More RAM would be the only lever — not expandable in the Mini.

**ngram speculation brings nothing for prose:** 32.3 tok/s with vs. 33.0
without. The 49.7 tok/s (+39%) measured in the meantime were an
artifact of repeatedly identical prompts at `temperature 0` — the drafter
memorizes its own output. **In speculation benchmarks,
always vary the prompts.** Structured output
(code), where n-grams might hit better, remains untested.
VRAM actually 107.5 GB across 5 cards (llama-fit-params projection hit
exactly), host RAM 4.5 GB. Load time 4:34–4:45 min.

**Variant comparison** (same hardware, same prompt):

| Variant | Result |
|---|---|
| `--load-mode auto` + lazy auto | **runs**, 107.5 GB VRAM / 4.5 GB RAM, 35.4 tok/s |
| `--tensor-read-lazy off` | **failed** — table goes into host RAM, aborted at RSS 17.8 GB |
| `--load-mode dio` | not applicable — no mmap ⇒ no lazy read ⇒ as above |

Random-read latency of the model disk (USB NVMe, O_DIRECT, 4 KiB): **209 µs**.
Extrapolated ~1.67 ms per token for 8 PLE lookups, so roughly 5% at 30 ms
per token. The share grows the faster the model gets.

**MTP is not available for this model in llama.cpp** (arch `qwen4exp`:
0 nextn/mtp tensors, `supports_mtp_export = False` in the converter) — in
contrast to the 27B (arch `qwen35`, 4 MTP tensors). No provider GGUF can
change that.

## Assessment

- **vLLM** (1Cat plus v100-skinny) beats llama.cpp in the sessions for the
  27B (~2×) and for Flash-Next (~1.7×) in generation — at 4-bit vs.
  Q6/Q8. For DeepSeek-V4-Flash, llama.cpp stays ahead.
- **MTP** boosts token generation (acceptance rates 90–96%), leaves PP
  untouched.
- **ub 2048** boosts prompt processing for MoE models massively
  (+53% to ~2.1×), leaves TG untouched. For dense models it is not
  worth it.
- End-to-end PP is systematically below the llama-bench values
  (server overhead, streaming, short prompts amortize worse);
  the llama-server's API `timings` are the most honest live value.
- **DSpark** (sidecar draft, DeepSeek-0731) acts on generation like MTP,
  but with lower acceptance rates (61–65% vs. 90–96%
  with MTP) and strongly content-dependent: structured code drafts
  almost twice as fast as free prose. The PP lead of
  V4-Flash does not come from the draft but from the architecture
  (43 layers, sparse attention indexer, cheap MLA KV).
